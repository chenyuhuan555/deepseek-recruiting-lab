# 先做一个岗位启动助手

状态：业务适配方案，尚未集成到应用。

## 当前问题

客户需求通常不是一次写清楚的。硬性条件、软性偏好和待确认事项混在一起，后续补充又可能改变原有寻访方向。助手需要帮助顾问把这些变化说明白。

首轮用户是负责接收需求、澄清和准备寻访的顾问。暂不扩展到候选人自动推荐或自动触达。

## 四项适配

| 调整 | 准备怎么做 | 需要验证什么 |
| --- | --- | --- |
| 固定角色 | 聚焦需求澄清、寻访准备、证据整理 | 是否减少泛泛建议，提出影响寻访的问题 |
| 统一岗位档案 | 保存确认条件、偏好、待确认项与版本记录 | 多轮补充后是否遗漏或错误覆盖条件 |
| 固定交付 | 岗位画像、客户追问、寻访假设及依据 | 顾问能否直接检查和继续使用 |
| 证据边界 | 区分客户原话、公开事实、助手建议 | 是否凭空补充薪资、经历或企业信息 |

## 需求变化怎样处理

客户先说“最好做过 HR SaaS”，记录为偏好。后来明确“必须有招聘产品经验”，新记录应增加硬性条件，并说明它与旧偏好的关系；不能自行认定两句话完全等价。

客户补充“不要求算法研发经验，但必须主导过产品上线”时，应：

1. 增加“主导产品上线”这一明确条件。
2. 将“不要求算法研发经验”记录为客户确认的非必要项。
3. 保留原始 RAG 参与要求，追问它与上线经历是否必须来自同一项目。
4. 对寻访方向提出待验证的调整建议，交给顾问确认。

## 当前与后续

当前可用提示模板进行人工对话，并手工维护岗位档案。

如果对照验证有效，再考虑让 Super-agent 接收需求变更、分派研究任务、交付待审核记录。届时还需要确认任务来源、身份、允许范围、失败处理及人工接管，不能仅凭模型能回答就启用自动执行。
