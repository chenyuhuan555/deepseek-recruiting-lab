# 岗位版本、带范围的反馈与证据：实现设计

日期：2026-11-03。

本方案是基于业务问题提出的独立实现设计，不是对 LinkedIn 内部系统的复刻。两个纯函数已经作为示例实现并测试。2026-11-04 在独立实验室实现了客户反馈模型草稿、同源 HTTP 接口及人工确认，见 [实测记录](feedback-draft-results.md)；本页数据库事务、持久化及完整生产权限模型仍为后续设计。

## 1. 为什么先用普通结构化记录

三种路径的取舍：

| 路径 | 优点 | 主要限制 |
| --- | --- | --- |
| 所有历史拼进提示词 | 很快可试 | 难以过期、区分范围和检查冲突 |
| 结构化记录 + 明确范围 + 人工确认 | 容易追溯和写测试，适合当前项目 | 需要顾问确认和维护数据 |
| 向量检索 + 自动偏好归纳 | 适合规模较大的相似案例检索 | 归纳错误与跨客户混用更难发现 |

本轮采用第二种。即使后续加入向量搜索，也先做账户权限、客户、岗位与有效期过滤，再做相似度检索。

## 2. 数据边界

| 对象 | 最小字段 | 约束 |
| --- | --- | --- |
| Job | id、client_id、current_version | 同一岗位每次确认修改生成新版本 |
| Criterion | id、text、kind、source_id、quote | kind 区分 required、preferred、not_required、unconfirmed |
| Revision | job_id、from_version、to_version、before、after、confirmed_by、confirmed_at | 追加保存，保留变更前后快照 |
| FeedbackMemory | text、scope、owner_id、source_id、confirmed_by、expires_on、status | scope 为 job、client 或 recruiter；草稿和过期记录不使用 |
| Evidence | criterion_id、job_version、source_id、quote、review_status、reviewed_by | 区分待核实、支持、不支持和信息不足 |
| Source | id、type、原始内容或内部受控引用、访问/记录时间 | 原始材料本身不授予任何执行权限 |

候选人意向单独记录候选人、确认内容与日期，不混入通用顾问偏好。真实部署还需在所有对象上加入组织隔离与访问控制；上表只是业务字段，不是完整生产数据库。

## 3. 从客户补充到新版本

```text
输入客户补充
  → 模型提出 patch 草稿（新增 / 替换 / 取消、原话、待确认问题）
  → 程序核对字段、条件编号与摘录
  → 顾问看差异，修改并确认
  → 服务端检查身份、权限和当前版本
  → 一个事务中保存新版本与变更记录
  → 标记需要重新复核的相关判断
```

模型只提出草稿。以“必须主导过产品上线”为例，新 patch 增加一个条件；旧的 B 端经验、RAG 参与和招聘流程要求不会因模型没复述而消失。需要取消的条件必须明确列出，顾问确认后才处理。

已实现的核心接口见 [core.py](../examples/scoped-memory/core.py)：

```python
updated = apply_change(
    job,
    expected_version=job.version,
    source_text='必须主导过产品上线',
    updates=(Criterion('launch', '主导过产品上线', 'required', '必须主导过产品上线'),),
    remove_ids=(),
    confirmed_by='reviewer-a',
)
```

纯函数会检查版本、确认人非空、字段分类与新增/替换条目的摘录，返回新的不可变快照并保留前一版本的条件。`confirmed_by` 在示例里只是一个参数，不是身份认证；生产服务必须从已登录且有权操作该岗位的会话取得它。

摘录匹配仅证明这段文字存在，不能证明分类或释义正确。取消条件目前只记录补充原文与被取消编号，语义对应仍需人工审核。原始材料录入、去重和语义冲突识别不在示例内。

## 4. 怎样阻止并发覆盖

纯函数的 expected_version 适合说明规则，不能独自解决多个进程同时写数据库的问题。生产保存必须在事务中执行条件更新，例如：

```sql
BEGIN;
UPDATE jobs
SET current_version = current_version + 1
WHERE id = :job_id
  AND current_version = :expected_version;
-- 受影响行数不是 1：ROLLBACK，返回版本冲突，要求重新加载差异。
-- 成功：在同一事务追加版本快照与来源、确认人、时间。
COMMIT;
```

这是事务思路，不是可直接执行的数据库迁移。权限检查、租户条件、快照插入、请求幂等键和重试处理需要与实际数据库一起实现。同一确认请求重试不能产生多个版本；下游重评任务用 job_id + version + action 去重。

## 5. 带范围的反馈怎样进入模型上下文

已实现的 `select_memories()` 接收当前岗位、客户、顾问和日期，只返回范围匹配、有人确认且未过期的记录。截止日期当天仍有效，未知范围不使用。输入应已完成访问权限过滤。

返回的偏好不能直接合并进硬性条件，应放入单独的 historical_suggestions 区域，让模型解释是否相关，并由顾问确认。

```json
{
  "current_requirements": "当前已确认的岗位条件和版本",
  "historical_suggestions": "经范围和有效期过滤的历史记录，仅作建议",
  "new_client_message": "本轮原文，作为待分析数据",
  "unresolved_conflicts": "尚需顾问裁定的矛盾"
}
```

“本客户暂不接受远程”不能影响其他客户。“顾问喜欢三句话摘要”可以影响表达，但不能变成排除候选人的条件。对同一范围内互相矛盾的记录，示例暂不裁定；后续先展示冲突，不按相似度或最新日期直接盖过已确认条件。

## 6. 证据卡怎样设计

建议每张卡展示：岗位条件及版本、来源类型、原文摘录、助手解释、人工核实状态、下一步问题。

示例：“主导上线”对应资料中“参与上线”，默认信息不足，询问负责范围、决策和上线结果。资料中没有证据，不自动得出没有经历。旧版本的候选人判断保留原关联，条件变化后标记待重评，不直接覆盖历史结论。

未来接口可为：创建变更草稿、确认变更、确认/撤回反馈、保存证据核实。草稿不允许直接指定真实确认人或执行外部动作；确认接口只接受用户审核的草稿内容和 expected_version。

## 7. 与 DeepSeek 如何连接

在调用模型前，由程序读取已授权的岗位快照、有效反馈和证据。要求模型输出结构化草稿；输出经过验证后送人工审核。模型不能直接修改数据库，也不能依据历史偏好自行发送消息。

本轮没有增加模型 API 调用、网页、数据库、ATS 或 LinkedIn 接口。后续先验证草稿分类与多轮修订，再考虑接入 Harness 或 Super-agent。历史信息中包含的命令只作数据，不作为工具调用授权。
